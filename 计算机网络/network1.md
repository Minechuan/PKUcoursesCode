# 计算机网络复习

## 第一部分：网络基础知识

### 1.1 网络实体
由三部分组成：网络边缘、接入网、网络核心

#### 1.1.1 网络边缘

**端系统**
端系统：位于互联网边缘与互联网相连的设备，如个人计算机、智能手机、服务器等。
主机：运行应用程序
内部结构：
1. 网络设备硬件：网卡（48 位 MAC 地址）。
2. 内核软件
3. 应用程序软件

主机名：字符串
#### 1.1.2 接入网
概念：连接端系统与互联网核心的网络部分，将主机连接到边缘路由器
边缘路由器：将主机连接到其他端系统的路径上的第一台路由器。
**物理介质**：
引导型介质：双绞线、同轴电缆、光纤
   * 双绞线：两根绝缘铜线相互缠绕，减少电磁干扰。常用于电话线和以太网连接。
   * 同轴电缆：由一根内导体、同心外导体和绝缘层组成，电缆结构能有效屏蔽外界电磁干扰。通过频分复用设计，可以实现上下行双向信号传输。
   * 光纤：利用光信号传输数据，带宽高，传输距离远。常用于长距离通信和高速互联网连接。

无线介质（非引导型介质）：
   * 无线电：电磁频段中各种波段携带的信号；无线链路类型：蓝牙、WiFi、卫星通信

**接入方式**
1. 数字用户线： DSL（Digital Subscriber Line）使用现有的电话线传输数字数据。
2. 同轴电缆：有线电视网络，提供高速互联网接入（调制解调器）。
3. 光纤到户（FTTH）：光纤直接连接到用户家庭或办公地点，提供高速互联网接入。
4. 无线接入：
   1. 无线局域网（WLAN）：如 WiFi，使用无线电波在局域范围内提供互联网接入。
   2. 蜂窝网络：如 4G、5G，使用移动基站提供广域范围内的互联网接入。

实际的家庭网络：采用有线和无线接入方式的结合，如光纤到户连接到家庭路由器，路由器通过 WiFi 提供无线接入。
企业网络通过交换机与专线直接接入 ISP。内部网络使用以太网交换机和 WiFi 连接终端设备。

#### 1.1.3 网络核心

目标：将海量端系统连接在一起
* 端系统通过本地网络服务提供商（access ISP）连接到 Internet。
* 每个 access ISP 通过专线连接到全局 global ISP。
* 区域 ISP 连接 access ISP 和 global ISP。

互联网公司也组建网络：content provider (CP) 网络，如 Google、Facebook。

### 1.2 网络服务

路由（规划：计算通目的主机的路径） + 转发（执行：每个结点将数据交给路径上的下一条）

#### 分组交换与电路交换
**分组交换**：将数据划分为较小的数据包（分组），每个分组独立传输。数据分组逐跳抵达目的地。
存储转发：每个结点接收完整的数据包后，才能向下一个结点转发。
**电路交换**：在通信双方之间建立一条专用的*通信连接*，实现端到端的*资源预留*，传输过程中保持该路径的独占性。
电路交换的多路复用：频分多路复用（FDM）、时分多路复用（TDM）。缺点：无法应对突发流量，资源利用率低，现在基本不使用。
>分组交换
>优点：
>  1. 更高的资源利用率
>  2. 适应突发流量。
>  3. 支持更多用户，用户在某个时刻传输数据的概率服从二项分布。
>
>缺点：
>1. 容易产生拥塞、排队甚至丢包
>2. 无法提供服务质量的保障（可以使用虚电路**折中**）


#### 网络服务的其他分类
**面向连接与无连接**
面向连接：在传输数据前，先建立连接，传输结束后释放连接。
无连接：每个数据包独立传输，无需建立连接。
**可靠传输与不可靠传输**
可靠传输：确保数据完整、按序到达目的地
不可靠传输：不保证数据完整性和顺序


#### 网络服务性能指标
1. 带宽（Bandwidth）：单位时间内网络中**某信道所能通过**的“最高比特率”。
2. 包转发率：交换机或路由器每秒钟能够**处理和转发**的数据包数量。线速转发：交换机在满负载下，能够以链路速率转发数据包。大包相比于小包更容易达到线速转发，因为处理每个包的开销较小，路由器的瓶颈在于“包数量”，而不是“字节数”。
3. 比特率：单位时间内 *主机* 往 *数字信道* 传输的比特数，通常以 bps（bits per second）为单位。
4. 吞吐量：单位时间内目的地实际接收到的数据量，通常以 bps（bits per second）为单位。受信道带宽、网络拥塞、协议开销等因素影响。
5. 有效吞吐量：单位时间目的地正确收到有用的数据量，排除协议开销和重传数据的影响。
6. 利用率：
   1. 信道利用率：实际吞吐量与信道带宽的比值。
   2. 网络利用率：全网信道利用率的加权平均值。
7. 丢包率：在数据传输过程中丢失的数据包数量与总发送数据包数量的比值。
8. 时延：数据从源主机传输到目的主机所需的时间，包括处理时延、排队时延、传输时延和传播时延。前3者与路由器相关，传播时延与链路相关。
   1. 处理时延：路由器处理数据包所需的时间。
   2. 排队时延：数据包在路由器队列中等待传输的时间。
   3. 传输时延：数据包从结点发送到链路上的时间，取决于数据包大小和链路带宽。
   4. 传播时延：信号在物理介质上传播所需的时间，取决于链路长度和信号传播速度。
#### 分析
分组交换中，分组到达速率超过链路传输速率时，产生排队和拥塞。
**Little's Law**: L（队列长度）= A（到达速率）* W（平均等待时间）
往返时延： RTT 指数据包从发送端发送到接收端，再从接收端返回到发送端所需的时间。
带宽-时延积（Bandwidth-Delay Product, BDP）：链路带宽与 *传播时延* 的乘积，表示在链路上“在途”的数据量。

### 1.3 网络协议
概念：为进行网络中数据交换而建立的规则、标准或约定
网络协议以头部封装的形式定义

#### 1.3.1 协议分层模型
分层的好处：
   1. 降低复杂性
   2. 增加灵活性

坏处：
1. 引入额外的开销
2. 舍弃了跨层信息


**OSI：Open Systems Interconnection**
七层模型：物理层、数据链路层、网络层、传输层、会话层、表示层、应用层
**TCP/IP**
四层模型：网络接口层、网络层、传输层、应用层
TCP/IP 的不足：未包含链路层和物理层的详细规范

数据链路层为 2 层；网络层为 3 层；传输层为 4 层；应用层为 7 层。

#### 1.3.2 网络分层的实现位置
端系统：所有层次均实现
边缘网与核心网：仅实现部分层次
 * 交换机：仅实现物理层和数据链路层
 * 路由器：实现物理层、数据链路层和网络层
现代交换机和路由器都支持 2 层与 3 层的功能。

**实现特点**
1. 复杂功能由端系统实现
2. 以 IP 为核心

**现有实现的局限性**
1. 各层功能重叠：严格分层的理想被打破，不同层为了解决同一问题，各自实现了相似功能，导致复杂性增加。
2. IP 协议难以升级：IP 位于网络核心层，一旦修改，涉及全网设备，升级成本极高。
3. 资源管理与性能控制依赖端系统：网络核心（路由器）只提供“尽力而为”服务，QoS 和性能主要由端系统负责。

## 第二部分：应用层

### 2.1 应用层基本概念

通信主体是应用程序，使用 IP 地址和端口号命名。

#### 客户端-服务器模型（Client-Server Model）
客户端发起请求，服务器响应请求，提供服务。
1. 客户端可以临时接入服务器，服务器通常长期在线。
2. 客户端可以使用动态的IP地址和端口号，服务器通常使用静态IP地址和端口号。

服务器可以采用循环方式（顺序服务，服务器只使用一个服务套接字）处理多个客户端请求，也可以采用并发方式（多线程、多进程、事件驱动）处理多个客户端请求。

1. 面向连接的并发方式：主服务进程监听套接字，收到连接请求后，创建子进程/线程，使用临时套接字处理该连接。临时套接字使用相同的端口号，但四元组唯一标识连接。
2. 面向连接的循环方式：服务器使用单个（连接）套接字，顺序处理每个客户端请求，每处理完一个客户端请求后关闭连接套接字。（仍然需要监听套接字）
3. 无连接无法采用并发方式。

#### 对等体模型（Peer-to-Peer Model, P2P）

对等方式指两个进程在通信中不区分服务的请求者和提供者，通信双方地位平等。


#### 名词解释：
1. WWW：World Wide Web万维网，构成：
   1. HTTP 服务器和客户端
   2. Web 对象，通过 URLs 定位
   3. HTTP 协议
2. Web 对象：Web 页面中的各种资源，如 HTML 文件、图像、视频等。
3. URL：Uniform Resource Locator，通用资源定位符，用于标识互联网上的资源位置。
4. 静态 Web 对象：内容固定不变的 Web 资源，如静态 HTML 页面、图像等。
5. 动态 Web 对象：交互信息，如用户注册、登录信息、数据库查询结果等。

CGI（Common Gateway Interface）：一种标准协议，定义在服务器创建动态文档的过程

### 2.2 HTTP 协议
无状态协议：每个请求独立处理，服务器不保存客户端状态信息。

#### 服务过程
1. 客户端向服务器发送 HTTP 请求报文
2. 服务器处理请求，生成 HTTP 响应报文
3. 客户端接收响应，处理数据


#### 各个版本

 * HTTP/1.0：每个请求建立一个新的 TCP 连接，传输完成后关闭连接。
 * HTTP/1.1：
   * 引入**持久连接**（Persistent Connection），允许在同一 TCP 连接上发送多个请求和响应，减少连接建立和关闭的开销。
   * 支持流水线传输（Pipeline），允许客户端在收到前一个响应之前发送多个请求，提高传输效率。
 * HTTPS：在 HTTP 基础上增加了 SSL/TLS 加密层，确保数据传输的安全性和完整性。
 * HTTP/2
   * 头部压缩（Header Compression），原本每个请求/响应都携带完整的文本头部，开销大
   * 服务器主动推送（Server Push），减少“被动等待客户端请求”的往返时延
   * 流量控制：允许应用层进行控制；TCP 流控对应用透明，而HTTP/2 流控由应用协议栈控制
 * HTTP/3
   * 基于 QUIC 协议，使用 UDP 传输，减少连接建立时间、提高传输效率。

#### 报文结构
1. 请求报文：开始行 + 首部行 + 实体主体
   1. 开始行： 请求方法 + URL + HTTP 版本
   2. GET Method：请求读取由 URL 指定的资源
   3. POST Method：向 URL 提交数据
   4. GET 与 POST 的区别：
      1. GET 请求将参数附加在 URL 后面，POST 请求将参数包含在请求体中。
      2. GET 请求有长度限制，POST 请求没有长度限制。
2. 响应报文：状态行 + 首部行 + 实体主体
   1. 状态行：HTTP 版本 + 状态码 + 短语
   2. 常见状态码：典型状态码包括：
      1. 200 OK：请求成功
      2. 301 Moved Permanently：请求对象被移走，在 Location 头部给出新地址
      3. 400 Bad Request：服务器不能解释请求
      4. 404 Not Found：服务器找不到请求的文档
      5. 505 HTTP Version Not Supported：服务器不支持请求的 HTTP 版本

#### HTTP 缓存
**浏览器缓存**：浏览器在本地存储已访问的 Web 资源，以减少重复请求，提高加载速度。
浏览器检查是否过期，通过 *条件 GET 请求* （If-Modified-Since 头部）询问服务器资源是否更新。
**代理缓存**：代理服务器缓存经过的 Web 资源，为多个客户端提供缓存服务，减少服务器负载和网络流量。
性能分析：
* 如果不使用缓存，传输时间为 互联网时延 + 接入链路时延 + 机构网络时延
* 使用缓存后，传输时间为：  不命中概率（接入链路+互联网时延） + 命中概率（机构网络时延）

询问式缓存更新：
* 客户端通过 If-Modified-Since 头部询问服务器资源是否更新。
* 服务器：
  * 资源未更新，返回 304 Not Modified 响应，客户端使用缓存资源。
  * 资源已更新，返回 200 OK 响应和新的资源内容，客户端更新缓存。
  
#### Cookies
Cookie 文件仅仅是文本串，没有可执行代码。
由于 HTTP 是无状态协议，Cookies 用于在客户端和服务器之间存储和传递状态信息。
1. 服务器在响应报文中通过 Set-Cookie 头部发送 Cookie 给客户端。
2. 客户端在后续请求中通过 Cookie 表明这个请求是之前的后续。
3. Cookie 保存在用户的浏览器中，可以包含用户偏好、会话标识等信息。
4. Web 服务器在数据库中以 Cookie 作为索引，保存与该用户相关的信息。

**Cookie 的好处**
1. 减少身份验证
2. 服务器获取浏览偏好

**隐私问题**
1. Cookies 可能被用于跟踪用户行为，侵犯用户隐私。
2. 获取 Cookie 伪造用户请求（爬虫）

HTTP 也可以使用 用户名+密码 进行基本认证，但不如 Cookies 灵活。

### 2.3 DNS 协议（Domain Name System）

多个域名映射到一个 IP 地址：如规范名和别名
一个域名映射到多个 IP 地址：可以实现负载均衡

**曾经使用的** hosts 文件仍然在操作系统中使用，优先级比 DNS 高。
**DNS 使用场景**：层次化、分布式的数据库系统，用于将域名转换为 IP 地址。
好处：避免单点故障、处理海量流量
域名结构：... .三级域名.二级域名.顶级域名

#### 域名服务器
也叫名字服务器，保存域树数据（相邻域名服务器的信息），负责域名解析。

1. 每个根服务器知道所有顶级域名服务器（TLD）的域名及 IP 地址。
2. 顶级域名字服务器：管理顶级域（如 .com, .org, .cn）
3. 二级域（权威）名字服务器：把所属域名划分为若干个区（*区* 小于等于 *域* ）
4. 本地 DNS 服务器（递归服务器）：通常由 ISP 提供，实际部署中解析请求路径上的本地域名服务器可能有多层

#### 域名解析过程

对用户透明：
1. 应用进程将域名放在 DNS 请求报文发给本地 DNS 服务器
2. 本地 DNS 服务器查询结果后，将 IP 地址使用应答报文返回给应用进程

**递归查询**：通常使用在主机向本地 DNS 查询
定义：当收到查询请求时，如果 DNS 服务器没有该域名的记录，则它会替用户向其他 DNS 服务器发起查询，直到找到结果或确定域名不存在，然后将结果返回给用户。

**迭代查询**：通常使用在本地 DNS 上，优先采用迭代查询上层域名服务器
定义：当收到查询请求时，如果 DNS 服务器没有该域名的记录，则它会返回下一步应该查询的 DNS 服务器 IP，用户（可能是某个 DNS 服务器）需要自己向下一级 DNS 服务器发起查询，直到找到结果或确定域名不存在。


具体步骤：
1. 主机向本地 DNS 服务器发送**递归查询**请求。
2. 本地 DNS 服务器若无缓存结果，则向根域名服务器发起**迭代查询**。
3. 根服务器返回相应顶级域名服务器的地址。
4. 本地 DNS 服务器继续以**迭代方式**向顶级域名服务器和权威域名服务器查询，直至获得最终解析结果。
5. 本地 DNS 服务器将结果返回给主机，并进行缓存。

#### DNS 报文格式

请求和相应报文结构基本相同
**基础结构部分**
1. 标志字段QR：查询时为 0，响应时为 1
2. Recursion Desired (RD)：表示客户端希望服务器进行递归查询
3. Recursion Available (RA)：表示服务器支持递归查询（用在返回地址中）

只有 RD=1 **且** 被查询服务器支持递归查询时，服务器才会进行递归查询

**问题部分**：查询名（域名或 IP 地址）、查询类型、查询类
**资源部分**：采用资源记录（Resource Record，RR）格式

#### 域名系统缓存
目的：提高查询效率，减少 Internet 服务器负载
缓存数据类型
   1. 缓存域名到 IP 地址的映射
   2. 缓存**顶级域**名字服务器的地址

主机一般也会缓存有关信息；缓存具有时限

#### 安全问题
所有的 DNS 报文均未加密，容易被篡改和伪造。
*通信链路窃听*：攻击者监听 DNS 查询和响应流量
*服务器收集*：**用户** 的每条查询信息被记录下来

**DNSSEC（DNS Security Extensions）**：
域名服务器使用私有密钥对资源记录进行数字签名，客户端使用公钥验证签名，确保数据完整性和真实性。
流程：
1. 一个支持 DNSSEC 的解析器向支持 DNSSEC 的服务器请求一个域名的 DNS 记录。
2. 解析器收到标准的 A 记录，同时收到一个 RRSIG 记录（资源记录签名），包含对 A 记录的数字签名。
3. 解析器请求该域的 DNSKEY 记录，包含用于验证签名的公钥。
4. 解析器使用服务器的 DNSKEY 记录和 DNSKEY 的 RRSIG 记录验证，确保 DNSKEY 记录未被篡改。
5. 一旦 DNSKEY 被验证可信，就可以使用它验证 A 记录的 RRSIG

### 2.4 电子邮件

#### 邮件系统组成 
用户代理（邮件客户端）、传送代理（邮件服务器）、协议
邮箱是邮件服务器中的一块内存，标识为电子邮件地址

#### 相关协议

**SMTP：Simple Mail Transfer Protocol，简单邮件传输协议**
1. Alice 撰写邮件
2. Alice 用户代理 (MUA) 通过 SMTP 将邮件提交给 Alice 的 MTA（SMTP 服务器）
3. Alice 的 MTA 作为 SMTP 客户端，将邮件传输到 Bob 的 MTA（SMTP 服务器）
4. Bob 的 SMTP 服务器将邮件存储在 Bob 的邮箱中
5. Bob 的 MUA 通过 POP3/IMAP 从邮箱中获取邮件

邮件必须为 ASCII 格式
SMTP 的不足：
1. 不包括认证
2. 仅支持 ASCII 格式
3. 邮件以明文传输，存在隐私问题

**最终交付（邮件访问）协议**
取邮件是一个“拉取”过程，不能使用 SMTP
1. POP3：Post Office Protocol version 3
   1. 认证：用户登录
   2. 用户 *收取电子邮件* , 将邮件标记为删除
   3. 退出登录，服务器删除标记为删除的邮件
2. IMAP: Internet Message Access Protocol
   1. 邮件服务器运行 IMAP 服务器进程
   2. 用户代理运行 IMAP 客户端进程
   3. 功能：
      1. 允许用户在**不同地方**使用不同计算机随时阅读和处理邮件
      2. 把每个邮件和一个 **文件夹** 关联起来
      3. 维护了用户的 **状态信息**
      4. 允许用户代理获取邮件某些部分
   4. 缺点：如果用户没有复制邮件，邮件一直在 IMAP 服务器上，之后每次查看都需要使用 IMAP 连接服务器，增加了服务器负担
3. Webmail: 基于 Web 的电子邮件服务
   1. 使用 Web 作为界面
   2. 用户及远程邮箱的通信通过 HTTP 协议完成



### 2.5 P2P 网络

#### 基本概念
每个实体都是一个对等结点
服务特点：
1. 不需要长期在线的服务器
2. 任意的对等结点可以直接建立连接
3. 对等结点可以随时加入或离开网络
4. 对等结点可以变换 IP 地址

优势：避免单一中心化服务器的性能瓶颈和单点故障
问题：Peer 索引，需要确定资源在哪个 Peer 上

**中心化索引**
由一个中心化服务器帮助检索：
1. 每个 peer 告知自身 IP 地址和所拥有的资源给中心服务器
2. 某个 Peer 需要某个资源时，向中心服务器查询

问题：单点故障、性能瓶颈

**Query Flood**
每个 peer 独立索引，记录自身所拥有的资源
通过 TCP 连接形成一个图（Overlay Network）
查询时，每个 peer 将查询请求转发给其邻居，递归查询，查到后原路返回。
问题：产生大量网络消息

**混合索引**
1. Overlay 组织为层次化结构，存在超级节点
2. 每个普通节点连向一个超级结点
3. 超级结点间采用去中心化


#### BitTorrent 工作原理
基于 P2P 的文件分发 **协议**
* 所有正在交换文件的 Peer 组成一个种子（torrent）
* 中心化的追踪器（tracker）服务器维护种子中所有 Peer 的信息，Peer 可以通过 tracker 获取其他 Peer 的 IP 地址

**工作流程**
1. 当一个 Peer 加入种子时，向 tracker 注册自己；
2. 随后从其他 peer 下载文件块。
   1. 下载过程中，Peer 之间交换拥有的 *文件块清单* 。
   2. 下载和上传文件可以同时进行
3. 与其他 peers 交换自己知道的 peers 信息
4. 获取整个文件块后，存在自私离开的可能

**优化策略**
1. 请求文件块时，选择罕见块优先下载（“懂得珍惜”）
2. 倾向于匹配上传和下载速度匹配的对等结点（“同类相亲”）
3. 一个结点为其他对等结点作出的贡献越大，它期望的回报就越大。（“有付出才有回报”）

发送文件块时：
1. Alice 向给自己发送数据最快的 4 个 peer 发送数据块
2. 每 10 秒钟，评估一次上传速率，选择新的最快的 4 个 peer 发送数据块
3. 每 30 秒钟，随机选择一个 peer 发送数据块（探索新连接）

**BitTorrent 遇到的问题**：
1. 下载速度不及预期
2. 版权纠纷
3. Peers 缺乏共享精神
4. 恶意 Peers 结点
5. 政府、主流网站封杀（例如 facebook 封杀链接）

#### 分布式哈希表（另一种索引方式）
如果没有中心化追踪器，是否可以实现 P2P?
核心挑战：如何管理 key -> peer 映射关系

**分布式哈希表**
以 Chord 为例（Chord 是一种分布式哈希表协议，用于实现高效、可扩展的节点查找和资源定位）：每个 peer 需要储存一些数据。
过程：
1. 开始时：
   1. 对所有的 peers 地址，以及资源 key 进行哈希
   2. 哈希值取模后，排列在一个圆环上
2. 当新的 peer 加入时，通知前驱和后续节点，更新它们邻居关系
3. 从后续 peer 迁移数据（相当于为后续 peer 分担节点压力）

正常退出：通知前驱和后续节点，更新它们邻居关系；将数据迁移给后续节点
异常退出：每份数据在多个 peer 备份，一旦发现某个 peer 异常退出，立即从备份 peer 恢复数据

实际中遇到的问题：
* 负载均衡：由于 hash 值不确定性，可能导致某些 peer 负载过重
* 不同的 peer 能力不一样

解决：将每个 peer 划分成多个虚拟结点，能力强的 peer 承担更多虚拟结点

### 2.6 Socket 编程

Socket：程序间调用网络发送/接收数据的接口
套接字描述符与文件描述符完全兼容

#### 创建和使用 Socket

1. 客户或服务器调用socket()创建本地套接字，返回套接字描述符
2. 服务器端：把本地 IP 和端口号与描述符socket_fd绑定(bind())

struct sockaddr（通用接口） 可以看作是 struct sockaddr_in 的“父类”（具体的 IPv4 接口）

#### UDP 套接字

sendto 时，直接在参数里指定目标，不用管目标是否接受数据（无连接）
recvfrom 时，直接接收数据
返回值为本次实际发送/接收的字节数
sendto 自动给 sockfd 分配端口

#### TCP 套接字
服务器端
   1. 创建套接字 socket()
   2. 绑定 bind()
   3. 监听 listen()
   4. 接受连接 accept()
   5. 数据传输 read()/write()
   6. 关闭连接 close()

关闭连接套接字的文件描述符并不会影响监听套接字
read/write: 与文件操作统一接口
send/recv: 针对网络程序，加入第四个参数用于控制数据发送或接收的行为

### 2.7 流媒体传输
概念：**连续的媒体（音频、视频）** 经过压缩编码、数据打包后经过网络发送给接收端，接收端重组、解码后 **按照时间顺序边接收边播放** 进行播放的过程。

特性：
1. 端到端的性能要求高
2. 时序要求严格
3. 具有一定程度的容错能力

#### 三种服务模式
1. 媒体点播：提前录制好的媒体文件，存储在流媒体服务器上，用户按需点播。
   1. 过程：
      1. 浏览器用户使用 HTTP GET 得到元文件
      2. **媒体播放器** 使用元文件中的URL，向媒体服务器发送请求，要求下载视频/音频数据
      3. **流媒体服务器** 将数据分成若干个数据包，通过 HTTP RESPONSE 发送给媒体播放器
      4. 媒体播放器边下载边解压缩边播放
   2. 遇到的问题：网络传输抖动
      1. 客户端使用缓冲区，设置阈值标记
      2. 缓冲区内容小于低阈值标记，加速传输
      3. 缓冲区内容大于高阈值标记，减速传输
2. 媒体直播：边录制边传输，边下载边播放
3. 实时交互：如视频会议、网络电话等，要求低延迟、高实时性

直播和实时交互使用 **信令协议**（如 RTSP，对建立的连接起控制作用）
**数据传输协议**（如 RTP/RTCP, 使音视频能够以时延敏感属性传输）

#### 流媒体传输协议
1. RTP（Real-time Transport Protocol）：为实时应用提供端到端的数据传输，但是不保证服务质量。关注时延敏感性
2. RTCP（RTP Control Protocol）：基于 UDP，与 RTP 配合使用，监控传输质量，提供丢包率、延迟、抖动等信息，帮助**监控**和**控制** RTP 流。
3. RTSP（Real-Time Streaming Protocol）（互联网遥控协议）：用于控制流媒体服务器上的媒体流的状态，支持播放、暂停、停止等操作。
   1. 没有定义编码方案
   2. 没有定义缓存方式
   3. 没有定义网络层传输时应该如何封装
   4. 既可以在 TCP 上传输，也可以在 UDP 上传输

| RTSP 功能    | 描述                 |
| ----- | ------------------ |
| 会话控制  | 建立连接、启动/暂停/停止流     |
| 资源管理  | 选择音视频流、切换码率、选择媒体资源 |
| 不承载媒体 | 本身不传输音视频，只传输控制消息   |

## 第三部分：传输层相关协议和考点
概念：将主机-主机之间的数据交付封装为进程-进程之间的数据交付
传输层无法提供延迟保证，带宽保证等服务质量保障
### 2.1 UDP 和 TCP 的比较

#### Socket

监听套接字（Listening Socket）：用于监听传入连接请求的套接字。
连接套接字（Connected Socket）：用于与特定客户端进行通信的套接字。也使用监听端口号；每个连接套接字都有一个唯一的四元组（源IP地址、源端口号、目的IP地址、目的端口号）来标识。


#### UDP（User Datagram Protocol）

发送、接收单位为数据报（Datagram）；应用层需要自己处理报文边界。（UDP 可选是否计算校验和）

#### 计算校验和的步骤：

1. 将数据报划分为16位字（16-bit word）；如果最后剩下一个字节，则在其后补0凑成16位。
2. 每次将一个整数与前面的和相加，若有进位则将进位加到结果的最低位（+1）。
3. 对最终结果取反，得到校验和字段的值。

链路层一般有检错纠错的功能，传输层的校验和主要用于检测数据在传输过程中是否被篡改或损坏。
伪头：不用于实际传输，只用于计算校验和，包括源 IP 地址、目标 IP 地址、协议号和 TCP/UDP 长度。
如果只对 TCP/UDP 报文自身计算校验和，无法发现数据报在 **IP 层/网络层**转发时出错（如源 IP、目标 IP、协议号出错），所以同时要计算伪头信息。


#### UCP 适合的应用：
1. 容忍丢包，延迟敏感的应用，如视频会议、实时语音通信等。
2. 以单次请求-响应为主的应用，如DNS查询、简单的请求-响应协议等。
3. UDP + 应用层 可能实现可靠传输（QUIC）。

### 2.2 TCP（Transmission Control Protocol）

建立在不可靠信道：损坏、丢失、重复、乱序的数据报；
#### 特点：
* 以字节流（Byte Stream）为单位进行传输；应用层不需要处理和划分报文边界。
* 全双工通信（Full-Duplex）；每个方向都有独立的缓冲区和控制信息。
* 可靠数据传输（Reliable Data Transfer）；通过序列号、确认号、重传机制等实现。
* 流量控制（Flow Control）；防止发送方发送数据过快，淹没 **接收方缓冲区**。
* 拥塞控制（Congestion Control）；通过调整发送速率，防止网络拥塞。


#### 停等协议（Stop-and-Wait Protocol）
一般性可靠传输机及性能优化
**几个可靠传输的版本：rdt(Reliable Data Transfer)**
1. 可能出错：
   1. rdt 2.0 引入 ACK 和 NACK，但是没有考虑 ACK 或 NACK 损坏的情况；
   2. rdt 2.1 通过使用序列号解决了这个问题，这里仅仅使用两个序列号。
   3. rdt 2.2 不需要使用 NACK，只使用 ACK。
2. 有错且可能丢包：
   1. rdt 3.0 引入超时重传机制，发送方在发送数据后启动定时器，如果在超时时间内没有收到确认，则重传数据。

效率分析：$F$ 是数据包大小（bit），$R$ 是信道传输速率（bps），$RTT$ 是往返时延（秒）。
$$
信道利用率=\frac{F}{R*RTT+F}
$$
长肥网络：带宽-延迟积（Bandwidth-Delay Product, BDP）较高。


### 2.3 流水线传输

效率分析(对于每次传输 3 个数据包)：
$$
U_{sender}=\frac{3L/R}{RTT+L/R}
$$


**滑动窗口**：循环使用有限的报文序号； 通常发送窗口的大小小于等于接收窗口的大小。
窗口大小不能超过 seq num 的一半，否则会出现歧义。

#### Go -Back-N (GBN)协议

**发送端**：维护一个计数器，对“最古老”未被确认的数据包设置定时器。
**接收端**
只需要记住下一个期望收到的数据包序号；丢弃所有乱序到达的数据包。
**累计确认**（Cumulative Acknowledgment）：乱序到达后，重新发送 **最后一个正确接收且按序到达的数据包** 的确认号。
**窗口大小 W**：最大可发送但未确认的报文数量 $W \leq MaxSeqNum -1$
#### 选择重传（Selective Repeat, SR）协议

**发送端**：只重传那些被认为丢失或损坏的数据包，为每个数据包维护一个单独的计时器。
**接收端**
对每个数据包单独确认（即每收到一个数据包，如果在接收窗口内则发送格各自 sequence number 的 ACK）；需要缓存乱序到达的数据包，直到所有前面的数据包都被正确接收。
如果收到窗口之前的数据包（[send base -N, send base-1]）需要对应发送 ACK，确保发送窗口能够滑动。
**窗口大小 W**：最大可发送但未确认的报文数量 $W \leq \frac{MaxSeqNum}{2}$
### 2.4 TCP 可靠传输机制

对字节流进行编号；每个字节都有一个序列号。ACK 为 **下一个** 期望收到的字节序列号。
#### 发送端
* 如果重传：最小序号的、未确认的报文段；启动定时器。（“已经出错，谨慎，每次只传一个”），避免超时设置过短导致频繁重传。
* 收到 ACK 后，滑动发送窗口，停止定时器，启动下一个未确认报文段的定时器。原因： ACK=100 丢失，在计时器还没有到期前，发送方收到了 ACK=200，此时发送方会认为 100-199 的数据都被正确接收了，从而滑动窗口。

**超时值设置**
发送端为发送的报文设置超时值,计算超时值的方法：
1. 测量 SampleRTT：从发送报文段开始，到收到对应 ACK 的时间间隔。
2. 估计 RTT：指数加权移动平均：$EsRTT = (1-\alpha) \times EsRTT + \alpha \times SampleRTT$，$sampleRTT$ 是最近一次测量的 RTT。
3. 估算 DevRTT：$DevRTT = (1-\beta) \times DevRTT + \beta \times |SampleRTT - EsRTT|$
1. 估计超时值：$TimeOut = EsRTT + 4 \times DevRTT$ 

只对 **一次发送就成功** 的报文测量 SampleRTT，避免重传影响。
有一些算法会在估计时考虑重传，**Karn 算法**：每重传一个报文段，超时值翻倍（指数退避，Exponential Backoff）。如果没有重传，使用 EstRTT 计算超时值。

**快速重传**：发送方在收到三个重复 ACK 后，立即重传对应的数据报文段，而不等待定时器到期。（不会更新计时器，因为计时器通常设置比较大）


####  接收端

简化后的 TCP ，缓存失序数据包，直到所有前面的数据包都被正确接收。但是发送 ACK 确认序号还是下一个期望收到的字节序列号。
**推迟确认**：减少通信量。但是会带来不必要的延迟。当收到一个报文段且之前的报文段均已被确认时，等待最多 500ms 以期望有数据报文段到达一起确认。测量 RTT 时，不要使用推迟确认的 ACK。


### 2.5 TCP 建立和关闭连接

#### TCP 选项

最大段长度 MSS, 窗口扩大选项 Window Scale Option（实际大小 = $size*2^{scale}$）；
允许选择 SACK：允许接收端指出缺失的数据字节。

#### 建立连接

两次握手由于 ACK 报文可能丢失，导致客户端误以为连接建立失败，再次发送请求报文。
三次握手：
1. 客户端发送 SYN 报文，进入 SYN-SENT 状态。
2. 服务器收到 SYN 报文，发送 SYN-ACK 报文
3. 客户端收到 SYN-ACK 报文，发送 ACK 报文，进入 ESTABLISHED 状态；服务器收到 ACK 报文，进入 ESTABLISHED 状态。

*避免新旧连接序号重叠*：使用密码池哈希函数，维护序号池。

#### 关闭连接

客户端或服务器任意一方都可以发起连接关闭。
四次挥手：
1. 主动关闭方发送 FIN 报文，进入 FIN-WAIT-1 状态。
2. 被动关闭方收到 FIN 报文，发送 ACK 报文，进入 CLOSE-WAIT 状态；主动关闭方收到 ACK 报文，进入 FIN-WAIT-2 状态。
3. 被动关闭方准备好关闭连接时，发送 FIN 报文，进入 LAST-ACK 状态。
4. 主动关闭方收到 FIN 报文，发送 ACK 报文，进入 TIME-WAIT 状态，等待 2 倍最大报文段寿命（MSL）后进入 CLOSED 状态。
5. 被动关闭方收到 ACK 报文，进入 CLOSED 状态。

其中 2 和 3 步可以合并为一个报文段完成。

**Syn 洪泛攻击**：攻击者发送大量伪造源 IP 地址的 SYN 报文，导致服务器资源耗尽，无法处理合法连接请求。
**TCP 端口扫描攻击**：SYN 扫描、FIN 扫描。从而识别目标主机上开放的端口，寻找潜在的漏洞。

### 2.6 TCP 流量控制与拥塞控制

#### 流量控制

接收窗口: 接收方告知发送方其可用的缓冲区大小，以防止发送方发送过多数据淹没接收方缓冲区。发送方限制未确认的数据量不超过接收窗口大小。

**非零窗口通告**：当发送方收到零窗口大小的通告后，停止发送数据；定期（坚持定时器）发送探测报文段，询问接收方当前的窗口大小。当接收方的窗口大小变为非零时，发送方恢复数据传输。（如果接收端还是零窗口，重启定时器）
**糊涂窗口综合症**：当数据的发送速度很快、而消费速度很慢时，接收方发送发送微小的非零窗口通告，导致发送方频繁发送少量数据，降低传输效率。
**接收方Clark Algorithm**：仅当接收窗口增加到 min(MSS, 缓存空间的一半) 时，才发送非零窗口通告，减少通告次数。
**发送方Nagle Algorithm**： 当有未确认的数据时，发送方将小数据段缓冲起来，直到收到之前数据的确认或积累了足够的数据（MSS 大小）再发送。

#### 拥塞控制
限制发送速度，不超过网络的承载能力，防止网络拥塞。
丢包事件：超时重传、三个重复 ACK。
拥塞窗口：$cwnd$，限制未确认的数据量不超过 min(拥塞窗口大小，接收窗口大小)。cwnd 决定的是：“在等待重传确认期间，能不能继续发新数据”。如果丢包，重传的是“最早未被确认的数据”，同时发送新数据。

**AIMD**：丢包后，拥塞窗口减半；每经过一个往返时间 RTT，拥塞窗口增加一个 MSS。

**1.慢启动**：每收到一个 ACK，拥塞窗口增加一个 MSS；*近似实现指数增长*。ssthresh：慢启动阈值。当 cwnd ≥ ssthresh 时，进入拥塞避免阶段。(由于图像曲线中横轴为 time 是针对 ACK 到达时间画的，所以看起来像线性增长）)
**2.拥塞避免**：每经过一个 RTT，拥塞窗口增加 MSS；每 RTT 大约有 cwnd/MSS 个 ACK，所以每次收到一个 ACK，窗口增大 MSS*(MSS/cwnd)；线性增长。
**3.快速恢复**：收到重复 ACK，cwnd 增加一个 MSS；收到新的 ACK，cwnd 设为 ssthresh，进入拥塞避免阶段 (之前的 ACK 没有白白浪费)。快速恢复阶段的 cwnd 是“虚高的”，并不代表真实的网络容量。

*TCP Tahoe*: 不区分超时重传和三个重复 ACK：都进入慢启动。ssthresh 设为 cwnd/2,cwnd 设为 1 MSS，
*TCP Reno* 引入快速恢复阶段，区分超时重传和三个重复 ACK：
| 当前阶段 | 条件              | 下一阶段        |
| ---- | --------------- | ----------- |
| 慢启动  | cwnd ≥ ssthresh | 拥塞避免        |
| 拥塞避免 | 超时丢包            | 慢启动：ssthresh 设为 cwnd/2, cwnd 设为 1 MSS|
| 拥塞避免 | 3 个重复 ACK       | 快速重传 + 快速恢复：ssthresh 设为 cwnd/2，将 cwnd 设为 cwnd/2+3MSS |
| 快速恢复 | 新 ACK           | 拥塞避免：cwnd 设为 ssthresh |




#### 公平性

AIMD 保证多个 TCP 连接在同一条链路上公平共享带宽资源。
但是如果应用建立多个并发连接，可能会占用更多带宽资源，导致不公平。


### 2.7 新型拥塞控制

**慢启动优化**：CWND 初始化为 10 个 MSS。
**TCP NewReno**:在快速恢复阶段，Partial ACK：接收方收到乱序数据包后，发送部分确认，表示已经收到的数据包，但没有对重传前数据包的确认。出现 partial ACK 说明有多个数据包丢失。继续重传未被确认的第一个数据包，直到再也不收到 Partial ACK 为止（直到所有丢失段都被确认），才结束快速恢复阶段。
**Selective ACK(SACK)**：使用 left edge 和 right edge 指定接收方已经正确接收的数据块。结合 ACK 可以确定没有收到的数据包。
**TCP-BIC (Binary Increase Congestion control)**（重点）
1. 丢包后，cwnd = $\beta$*cwnd,设置 Wmax 为当前 cwnd; 
2. 每一个 RTT， 若无丢包，cwnd = (Wmin + Wmax) / 2，然后更新 Wmin 为当前的 cwnd.
3. 当 cwnd 超过 Wmax 时，采用与逼近 Wmax 时对称的方案，继续增加 cwnd。

不公平性：RTT 较短的连接会更快到达满载窗口。因为 TCP 的窗口增长是以 RTT 为“时间单位”进行的，RTT 越短，单位时间内增长次数越多。
**TCP CUBIC（Cubic Congestion Control Algorithm）**（重点）
窗口增长独立于 RTT，使用立方函数控制 cwnd 增长。取决于当前时间与上次丢包时间的差值。
$W_{max}$：上次丢包时的 cwnd 大小；$K$：从上次丢包到 cwnd 增长到 $W_{max}$ 所需的时间；$C$：调整因子。
$$
W(t)=C*(t-K)^3+W_{max} \\
K = \sqrt[3]{\frac{W_{min}}{C}}, W_{min} = \beta*W_{max} 
$$
区间的宽度不再依赖于 ACK(TCP BIC 利用 ACK 测量 RTT)。
**TCP Vegas**：使用 RTT 的值来影响拥塞窗口，而不是通过丢包事件。
1. 计算期望速率和实际速率的差值 Diff。
2. 根据 Diff 调整 cwnd：
   - 如果 Diff < α，增加 cwnd（线性增加）。
   - 如果 Diff > β，减少 cwnd（线性减少）。
   - 否则，保持 cwnd 不变。
  
**TCP Westwood**：主要用于无线网络环境，通过检测 ACK 的到达速率来估计带宽。
**TCP BBR(Bottleneck Bandwidth and Round-trip propagation time)**：（重点）
瓶颈链路带宽，不会引起排队的最大速率。
BDP = 瓶颈链路带宽*整个路径往返时间，认为 BDP 是最优的窗口大小。
但是 MaxBW 和 MinRTT 不能同时被测得。BDP 近似检测：
用过去 10s 的最小 RTT 和最大投递率分别近似 RTprop 和 BtlBW。

1. 启动阶段：指数增加发送速率，直到三次发现投递率不再增长。
2. 排空阶段：指数降低发送速率，将多占的数据排空，进入稳定阶段。
3. 带宽瓶颈探测（长期处于，试探性提高发送速率，如果发现更高带宽则更新，否则排空额外增加的带宽）：持续验证是否存在更高的可用带宽
4. 时延探测 200ms（2% 的时间）：用于探测 RTprop

问题：存在霸凌行为，loss-based 拥塞控制会选择退让，而攫取带宽的 BBR 不会退让。

**DCTCP(Data Center TCP)**（重点）
incast: 多个发送方同时向一个接收方发送数据，大量流量到达交换机的一个端口，导致交换机缓冲区溢出，造成大量丢包和延迟增加。
Queue BuildUp: 长流和短流到达同一个端口，长流占用大量缓冲空间，导致短流延迟增加。
Buffer Pressure: 交换机不同端口使用同一个缓冲区，短流仍然被长流“欺压”。

*目标*：
1. 容忍高突发流量
2. 短流低时延
3. 长流高吞吐量

*交换机*：当队列长度超过K时，给随后到来的包标记ECN。
*接收端*：当 ECN 标记的报文出现或消失时立即发送 ACK，否则延迟发送 ACK。
*发送端*：每个 RTT 更新一次发送窗口：
   * $M_{total}=\frac{RTT 内 ACK 前进字节数}{MSS}$
   * 统计其中 ACK 报告 ECN 的比例得到 $M_{ECN}$
$$
\alpha = (1-g)*\alpha + g*F \\
F = \frac{M_{ECN}}{M_{total}} \\
cwnd = cwnd*(1-\frac{\alpha}{2})
$$
$0<\alpha<1$, $\alpha$ 越大，拥塞越严重，窗口减少越多。


*优势*：传统 TCP 中通过丢包来判断拥塞（这时候网络中已经有严重的排队现象了），而 DCTCP 通过 ECN 标记来判断拥塞，能够更早地感知网络拥塞状况，从而更有效地控制发送速率，减少丢包和延迟。
1. 降低排队长度，可以处理更高的突发流量。
2. 减少丢包，提高短流的时延性能。

### 2.8 新型传输层协议
#### DCCP (Datagram Congestion Control Protocol)
**基于 UDP**
UDP 没有拥塞控制机制，DCCP 在 UDP 的基础上增加了拥塞控制功能，适用于实时应用。（提供不可靠的数据流服务）
DCCP：全双工、面向连接（两个方向的半连接，相比于 TCP，一方的 data 和 ACK 是分开传输的），两个半连接可以由应用层选择不同的拥塞控制算法。
**TCP-like Congestion Control**：类似于 TCP 的拥塞控制机制，适用于需要可靠传输的应用。
**TCP-Friendly Rate Control (TFRC)**：适用于实时应用，基于接收端的丢包率来调整发送速率，提供平滑的传输速率。
与 TCP 不同的是，其中 SeqNum 与 ACK 仅仅是用于拥塞控制算法，并不用于可靠传输。

#### MPTCP (Multipath TCP)
**基于 TCP 的改进**：将单一数据流切分为若干 TCP 子流，在多个路径上并行传输数据，提高带宽利用率和连接的可靠性。
MPTCP 向应用层“单条”连接的抽象。对应用层和网络层都是透明的。
每个路径由一个四元组（源IP地址、源端口号、目的IP地址、目的端口号）唯一标识。子流：在单个路径上运行的 TCP 流。
发送端根据将数据按照合理的调度算法分配到不同的子流上。
接收缓冲区需要处理不同路径乱序到达的数据包。
**公平性**是关注的重点：MPTCP 连接在共享路径上不会占用比单路径 TCP 连接更多的带宽资源。通过限制各个子流窗口增长的速度的总和。

#### QUIC (Quick UDP Internet Connections)
TCP 的局限：
1. 应用程序无法修改拥塞控制算法
2. 三次握手握手时延大
3. 多流复用时存在队头阻塞问题（后面的数据需要等待前面丢失的数据到达）

QUIC = UDP + TLS等特性

1. 一个 RTT 完成握手，减少连接建立时延。
2. 在单个 QUIC 连接中，**可以并行承载多个相互独立的流（stream）**，每个流内部保持有序，而不同流之间互不阻塞，从根本上消除了 TCP 多流复用下的队头阻塞问题。

QUIC 的特点：
1. 在数据传输机制上，QUIC 以 **frame 为基本承载单元**，实现 ACK与数据向上层交付的解耦（数据（STREAM帧）向上层交付的依据是 Stream ID 和 Stream Offset，而不是 TCP 的字节流序列号）。
2. QUIC 使用 **单调递增且不复用的 packet number** 标识每一个报文段，即使发生重传也会分配新的编号，从而避免了 TCP 中因序列号复用而产生的歧义，并使 RTT 测量更加精确可靠。
3. QUIC 通过 **Connection ID** 标识逻辑连接，使连接不再依赖于固定的五元组，从而支持在网络切换（如移动场景中的 IP 变化）时实现无感知的连接迁移.
